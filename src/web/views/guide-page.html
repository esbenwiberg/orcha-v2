Getting Started

Orcha is a terminal session manager for orchestrating Claude Code sessions across repositories

Orcha lets you spin up isolated Claude Code sessions, each with its own terminal, repository checkout, and optional credentials. You manage everything from this dashboard — no need to juggle multiple terminal windows.

The typical workflow is: add a repo, create a preset (optional), then launch a session.

Sessions

The core unit of work

A session is a terminal process running Claude Code against a specific repository. Each session gets its own PTY, worktree, and lifecycle.

Creating a session

  1. Click + New Session in the header (or From Preset to start from a saved template)
  2. Select a repository from the dropdown
  3. Pick a source branch (dropdown loads on click)
  4. Optionally select a model config to use a custom provider (Anthropic API, Azure, local)
  5. Optionally attach a credential profile for cloud access
  6. Optionally select MCP servers to inject into the session
  7. Write a prompt — the initial instruction for Claude
  8. Hit Create

Terminal

Click a running session card to expand the inline terminal. The terminal is a full xterm.js instance — you can type, scroll, and resize. Click the card header again to collapse it.

Session card tools

Each session card has a toolbar with quick-access buttons:

Debug shell

From the More menu, you can open a debug shell — an interactive bash terminal inside the session's worktree. Useful for inspecting files, running tests, or checking environment state while the agent is working.

Voice input

On supported browsers, the terminal includes a microphone button for voice-to-text input. Press it, speak your instruction, and it will be transcribed and typed into the terminal.

Tasks

Autonomous task pipeline with kanban board

Tasks let you queue work items that Orcha processes autonomously — from investigation through to a finished pull request. You manage tasks on a kanban board; Orcha handles the rest.

Creating a task

  1. Go to the Tasks page
  2. Click + New Task
  3. Select a repository and optionally a preset to pre-fill settings
  4. Write a title and description — the description is the instruction for the agent
  5. Optionally paste screenshots (Ctrl+V) to attach images
  6. Hit Create — the task lands in the Inbox column

Pipeline stages

When you drag a task from Inbox to Investigating (or it advances automatically), Orcha runs a multi-stage pipeline:

StageWhat happens
InvestigateClaude reads the repo and task description, produces a structured analysis (affected files, approach, risk)
EnrichThe investigation is used to generate a detailed execution plan and branch name
ExecuteA full Claude Code session runs in an isolated worktree, implementing the plan
PROn success, a pull request is created on GitHub or Azure DevOps

Kanban columns

ColumnStatusesMeaning
InboxDraftWaiting to be picked up
InvestigatingInvestigatingAgent is analyzing the task
ReviewRejectedInvestigation was rejected — edit and retry
PipelineEnriching, Queued, ExecutingActively being processed
DoneDonePR created or task completed
FailedFailed, CancelledSomething went wrong or was stopped

Real-time updates

The kanban board updates live via SSE (Server-Sent Events). Cards animate between columns as tasks progress, and activity indicators show when an agent is actively working. A needs input badge appears when the agent is waiting for user interaction.

Task actions

  • Drag-and-drop — move cards between columns to advance or reset tasks
  • Terminal button — jump straight to the active session terminal
  • Edit — update title, description, or screenshots on draft tasks
  • Retry — reset a failed task back to draft for another attempt
  • PR review — after a PR is created, Orcha can fetch review comments from GitHub/DevOps, run a follow-up session to address them, and post a summary

Task pipeline settings

Configure how many tasks run in parallel and other pipeline behavior under Settings → General tab → Task Pipeline.

Presets

Reusable session templates

Presets save a combination of settings so you don't have to re-enter them every time you create a session.

What a preset stores

  • Name — a label for the preset
  • Repository — which repo to check out
  • Model config — optional model provider override
  • Credential profile — optional cloud credential template
  • MCP servers — which MCP servers to inject into the session
  • Allowed tools — Claude Code tool permissions

To use a preset, select it from the dropdown when creating a new session. All fields are pre-filled but can be overridden.

Repositories

Git repos available for sessions

Before you can launch a session, you need to register at least one repository.

  1. Go to the Repos page
  2. Click + Add Repo
  3. Enter the local path or clone URL

Each session checks out the repo into an isolated git worktree, so multiple sessions can work on the same repo simultaneously without conflicts.

Credentials

Scoped cloud access for sessions

Credential profiles define what cloud access a session gets. When a session starts, credentials are provisioned; when it ends, they're automatically revoked.

Supported providers

Provider Mechanism
AzureService principal via DefaultAzureCredential + Graph API
GitHubFine-grained personal access token via REST API
Azure DevOpsPAT via VSSPS API

Direct PAT mode

Azure DevOps profiles support a Direct PAT mode — instead of provisioning a short-lived token via the VSSPS API, the session uses the bootstrap PAT directly. Useful when your org restricts PAT creation APIs.

Credential isolation

When a credential profile is attached, Orcha strips ambient tokens (like AZURE_DEVOPS_EXT_PAT) from the session environment so the agent can only use the scoped credentials you configured — not whatever happens to be set on the host.

Create profiles on the Credentials page, then attach them when creating sessions or presets.

Validation

Sessions can spin up and test the app they're working on

Orcha exposes an MCP server to each session so Claude Code can build, start, and health-check the application under development — without breaking out of the sandbox.

How it works

  1. Configure validation on the Repos page (edit a repo → Validation Config section) or override per-preset
  2. Choose a mode: serve (run a process on a port) or docker (docker compose)
  3. When a session starts, Orcha injects an MCP server URL into the session's .claude/settings.json
  4. The agent calls validate_start to build and launch the app, then validate_status or validate_logs to check progress
  5. When done, validate_stop tears it down — or it auto-stops on session exit or timeout

MCP tools available to sessions

Tool Description
validate_startBuild, start, and health-poll the app. Returns the URL and port.
validate_stopGracefully tear down the validation environment
validate_statusCheck current status, URL, port, and uptime
validate_logsGet recent stdout/stderr output from the running app
validate_browseNavigate to a page and return a screenshot + console errors (Playwright)
validate_screenshotCapture the current page or a specific CSS selector
validate_extractExtract text, HTML, or attributes from elements matching a CSS selector
validate_consoleReturn buffered browser console logs
validate_handoffPause and hand browser control to the user for login/MFA, then resume with authenticated state

Live preview

Once the agent calls validate_start, you can open the running app directly in your browser. Click the Preview (globe) button on the session card, or navigate to /validate/<sessionId>/. Orcha reverse-proxies all HTTP and WebSocket traffic to the validation app — Vite HMR, SignalR, SSE streaming, and static assets all work transparently.

Configuration sources (layered, later wins)

  1. .orcha/validate.yml in the repo (version-controlled)
  2. Validation fields on the repo (set in the Repos edit form)
  3. Validation overrides on the preset
  4. Parameters passed directly to validate_start

Browser handoff

Some apps require human interaction to authenticate — login forms, MFA, CAPTCHAs. The validate_handoff tool lets the agent pause and hand browser control to you.

  1. Agent calls validate_handoff(url, message)
  2. Orcha shows a notification in the UI with the agent's message (e.g. "Please log in to Dataverse")
  3. You interact with the browser in the Orcha-hosted window
  4. Click Done (or a wait_for CSS selector auto-triggers completion)
  5. The agent resumes with the authenticated browser state — cookies, tokens, and DOM persist

Optional parameters: proxy (HTTP proxy URL), wait_for (CSS selector for auto-completion), timeout (default 5 minutes).

Remote Docker VM

When running on hosts without Docker (e.g. Azure Container Apps), validation can target a remote Docker VM. Set DOCKER_HOST=ssh://orcha@<vm-ip> and Orcha routes docker compose commands over SSH. Provision a VM with bash scripts/deploy-docker-vm.sh.

Teardown guarantees

Validation environments are cleaned up via four layers: agent explicit stop, session exit handler, periodic cleanup sweep, and configurable timeout (default 5 minutes).

Inter-Session Messaging

Sessions can talk to each other

Sessions can communicate asynchronously using MCP messaging tools. This enables coordination between agents working on related tasks — one session can ask another for context, share findings, or request help.

Direct messages

Fire-and-forget messages from one session to another. The recipient sees a PTY notification and can read messages with read_messages. Address sessions by display ID (e.g. "42") or UUID.

Collaboration channels

For structured back-and-forth conversations:

  1. Session A creates a channel with create_channel(topic, max_exchanges)
  2. Session A invites Session B (auto-sends a direct message with join credentials)
  3. Session B reads the invite and joins with join_channel()
  4. Both sessions exchange messages via reply() — each reply counts toward the exchange limit
  5. Either member closes with close_channel(summary)

Channels auto-close when the exchange limit is reached or after 1 hour. Summaries persist for later reference.

MCP tools

ToolDescription
send_messageSend a one-way message to another session
read_messagesRead unread direct messages or channel messages
create_channelStart a collaboration channel with a topic and exchange limit
join_channelJoin an existing channel with the join secret
replySend a message in a channel
close_channelClose a channel with a summary

Session History

Transcript capture and analysis

Orcha automatically captures Claude Code conversation transcripts (JSONL format) when sessions end. These are stored persistently and survive session deletion.

What gets captured

  • Full JSONL conversation transcripts (human, assistant, and system messages)
  • Per-turn cost and duration metadata
  • Session metadata: repo, branch, message count, capture time

Browsing history

The History page lists all captured sessions sorted by most recent. Click a session to see individual JSONL files with message previews, or download the combined transcript for external analysis.

Admin analysis sessions

Select one or more history entries and click Analyze to spin up a read-only analysis session. The session gets symlinks to the selected history directories and a CLAUDE.md guide explaining the JSONL schema. You can pick a model config for the analysis session — useful for running cost analysis, identifying patterns, or auditing agent behavior across sessions.

Custom model providers

The Models page lets you configure alternative model providers for sessions. Each config defines how Claude Code connects to the model API.

MCP Servers

Extend sessions with custom tools

MCP (Model Context Protocol) servers expose additional tools to Claude Code inside sessions. Orcha has a built-in validation MCP server, and you can register your own.

Adding an MCP server

  1. Go to Settings → Integrations tab → MCP Servers
  2. Click + Add Server
  3. Choose a type: HTTP (Streamable HTTP) or Command (stdio-based)
  4. Enter the URL or command

Registered servers appear as checkboxes when creating sessions or presets. Selected servers are injected into the session's Claude Code config on startup.

The built-in validate MCP server is always available — it doesn't need to be registered.

Skills

Global slash commands for all sessions

Skills are reusable prompt templates exposed as /slash-commands inside Claude Code sessions. Define them once, and every session gets access.

Managing skills

  1. Go to Settings → Integrations tab → Skills
  2. Click + Add Skill
  3. Give it a name (becomes the /command) and write the prompt template

Inside a session, the agent (or you) can invoke /skill-name and Claude Code will expand it to the full prompt.

Settings

Global configuration for all sessions

The Settings page is organized into four tabs.

General

  • Azure CLI — host-level az sign-in status for deployments
  • Task Pipeline — configure how many tasks run concurrently in the background processor
  • Git Identity — user.name and user.email injected into each session's .gitconfig

Agent

  • CLAUDE.md — global instructions injected into every session
  • soul.md — voice and style guide merged into CLAUDE.md at session start
  • Claude Permissions — tool allow/deny rules written to .claude/settings.json

Integrations

  • Private Feeds — Azure DevOps Artifacts feed config (org, project, PAT, feed names). When enabled on a session, Orcha injects .npmrc and NuGet.Config with authentication so agents can install private npm and NuGet packages.
  • Global SDKs — enable TypeScript, .NET, or other SDKs installed at container boot
  • MCP Servers — register custom MCP servers to inject into sessions (see MCP Servers section)
  • Skills — define custom /slash-commands available in all sessions (see Skills section)

Credentials

  • Bootstrap PATs — long-lived tokens used by credential providers to provision short-lived session credentials. PATs are validated on save with immediate feedback.

System

Health monitoring and cleanup

The System page shows uptime, disk usage, and resource stats.

Cleanup

A background CleanupService runs automatically on startup — it prunes expired credentials, orphaned worktrees, and stale session data on a schedule. You can also trigger cleanup manually:

  • Clean logs — remove old session log files
  • Clean worktrees — prune orphaned git worktrees from finished sessions

Self-deploy

If configured with Azure Container App credentials (DEPLOY_* env vars), the System page shows a Deploy button that builds and pushes a new container image via ACR Tasks, then updates the Container App revision. The deploy log streams in real-time.
